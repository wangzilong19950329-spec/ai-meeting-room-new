## 2. Current known issue: why single execution has only search and no analysis

The latest discussed meeting was:

```text
迈瑞医疗 300760 2026下半年价格区间概率分析-0528
```

Observed database state from the current local MySQL during this session:

```text
ai_meeting_room.id = 37
ai_workflow_run.id = 37
workflow status = CONCLUDED
template_key = smoke-analysis-review-231108
analysis stage attempts = 1..7
review rejections = 1..6
review attempt 7 = APPROVED
```

The final approved "analysis" was not a real analysis. It was mostly:

```text
实际搜索计划
命中来源
关键字段
冲突信息
缺失信息
证据表
```

The content did not provide the actual node-level analytical deliverable. The review node eventually approved because the source coverage looked acceptable, even though the analysis deliverable was missing.

Root cause:

The single DeepSeek Web execution is currently framed as a "web researcher" task. The prompt contract asks it to produce search artifacts first. The backend then accepts this DeepSeek Web output as the node output. Therefore the single execution completes the "search report" part and the system treats it as the "analysis node" result.

This is not primarily a frontend truncation bug, not only a bridge extraction-timing bug, and not only a search-quality bug. Those can still exist, but the root problem here is the execution contract:

```text
current behavior:
node requires analysis
backend asks DeepSeek Web to act like researcher
DeepSeek Web returns research/source report
backend stores that as analysis node output
review sometimes approves it
```

Desired behavior:

```text
node requires a deliverable
backend asks the model to fulfill that node deliverable
search happens only as supporting work
search plan/sources/evidence are stored as trace or appendix
main output must answer the node task
```

## 3. Design direction the user wants

The user repeatedly clarified:

1. The design must be generic, not stock-specific.
2. Each member/actor should be able to independently decide what to search.
3. Previous speakers' evidence can be visible as context, but it must not replace the actor's own independent judgment.
4. If the meeting prompt or workflow node prompt constrains search sources, the model should obey that prompt.
5. If the prompt does not constrain sources, the system must not inject old constraints like "must hit 巨潮资讯".
6. `projectContext` or human background notes should be auxiliary context, not a hidden execution-control plane.
7. The system should approximate DeepSeek Web behavior: the model sees the user task, decides search plan, searches, and then answers the task.

Strong no-go list:

```text
Do not hardcode "price task".
Do not hardcode "probability task".
Do not hardcode stock data fields.
Do not hardcode 迈瑞医疗 or 300760.
Do not hardcode source requirements like 巨潮资讯 unless the current prompt says so.
Do not let a search trace become the main node answer.
```

## 4. Recommended next implementation

Implement a generic "node deliverable contract".

Suggested class shape:

```text
WorkflowNodeExecutionContract
- stageKey
- stageName
- actorName
- actorRole
- skillPrompt
- nodePrompt
- reviewPrompt
- meetingTask
- requiredDeliverableText
- forbiddenMainOutputText
- tracePolicy
```

This contract should be built from the workflow stage template, actor template, meeting title/description, current workflow handoff, and review requirements.

The prompt to DeepSeek Web should say, in generic terms:

```text
You are the executor of this workflow node, not a search-report writer.
Your first responsibility is to produce the node deliverable defined below.
Use web search only as a tool to support that deliverable.
Do not make "search plan / source list / missing fields" the main body.
If evidence is incomplete, still provide the best supported deliverable, mark assumptions and uncertainty, and put search trace in appendix.
```

Then include:

```text
Current node deliverable:
<derived from stage prompt, skill, role, review criteria>

Current meeting context:
<meeting state packet>

Evidence trace requirement:
Put search plan, sources, conflicts, gaps, and citations in appendix or structured trace.
```

The key is that the "deliverable" is dynamic and prompt-derived. It is not based on topic keywords.

## 5. Single-call vs two-phase

There are two viable implementation paths.

Path A - fix the single call:

Use one DeepSeek Web call, but rewrite the prompt so the main answer must be the node deliverable and search artifacts are appendix only.

Pros:

```text
Simpler.
Less bridge traffic.
Lower risk of account rate/mute issues.
Closer to user's current mental model of one actor thinking/searching/answering.
```

Cons:

```text
Still depends on DeepSeek Web not stopping after search trace.
Bridge may still capture before the model reaches appendix/final answer if extraction timing is weak.
```

Path B - explicit research then synthesis:

First call asks for research dossier. Second call asks for node deliverable from dossier and forbids search-report-as-main-output.

Pros:

```text
More controllable.
Easier to debug.
Can store research and answer separately.
```

Cons:

```text
More Web calls.
Higher account-risk if many actors run.
More latency.
```

Given the user's account limit and risk of muting, start with Path A unless it still fails. But even with Path A, store the trace separately so the frontend can show it without polluting the meeting record.

## 8. Known secondary bugs / risks

The database search trace for meeting 37 did not include all bridge extraction state such as content status or completion reason. The backend currently stores provider/status/note/queryCount/resultCount/timing/isolation-like data, but not enough raw extraction diagnostics.

Recommendation:

```text
Persist raw bridge status fields:
- contentStatus
- completionReason
- answerSource
- targetId
- isolatedSession
- raw answer length
- whether output was accepted as node deliverable
- whether output was only trace/research appendix
```

### 8.2 Review node approved a non-deliverable

Attempt 7 was approved even though it looked like a search/source report. This is secondary to the execution-contract bug, but still needs hardening.

Do this generically:

```text
Before review approval, ask:
"Does this output satisfy the current node deliverable?"

Do not ask:
"Does this output contain enough sources?"
```

This can be an LLM judge based on the same node deliverable contract. Avoid domain keyword validators.

Some backend trace structures and frontend rendering changes exist, but this should be reviewed end to end in browser after the main deliverable-contract fix.

## 9. Suggested concrete next patch

1. Add a small internal contract builder in `MeetingWorkflowService`.
2. Rename or conceptually split `buildWorkflowDeepSeekWebSearchTask` into `buildWorkflowDeepSeekWebNodeExecutionTask`.
3. Change the DeepSeek Web prompt order:

```text
Identity:
You are the current workflow node executor.

Primary deliverable:
<dynamic node deliverable contract>

Rules:
- The main body must satisfy the primary deliverable.
- Search is supporting work only.
- Do not start with search plan/source list unless the node deliverable itself asks for a search report.
- Put search trace in appendix.
- If data is incomplete, produce a provisional deliverable with assumptions and uncertainty.
```

4. Change direct-output acceptance:

```text
Only accept DeepSeek Web content as stage output if it satisfies the node deliverable contract.
Otherwise keep it as search trace and synthesize/follow up.
```

5. Store trace and deliverable separately:

```text
submission.content = node deliverable
search_trace.raw_content = search/research trace
search_trace.accepted_as_deliverable = true/false
```

6. Make the review node judge the node deliverable, not the search trace.

If implementing a generic deliverable judge, use an LLM prompt fed with:

```text
node deliverable contract
candidate output
review criteria
```

Return JSON:

```json
{
  "satisfiesDeliverable": true,
  "reason": "...",
  "missing": ["..."],
  "isSearchTraceOnly": false
}
```

Again, do not make this judge stock-specific.
