### 2.2 Web prompt slim — 去掉定向来源约束

**这是真正的 hallucination 杀手**。

`buildWorkflowDeepSeekWebSearchTask` 之前会注入：
- 优先来源列表（"必须命中巨潮资讯"等）
- 必须核验字段（"当前股价、净利润..."）
- 节点偏好约束

测试发现，注入这些约束 = 教模型怎么编 `[来源1][来源2][来源3]`。删除约束后，模型行为质变：

| meeting 39 (宁德时代) | 6 个 `[来源N]` | — |
| meeting 41 attempt 1 | 7 个 | — |
| meeting 41 attempt 2 | 11 个 | — |
| **meeting 43 attempt 2 (新)** | — | **0 个**，且 judge 准确指出"未标注信源" |

新 prompt 现在告诉模型：
```
搜索方式：你完全自主决定搜什么、用什么关键词、综合哪些来源。系统不限定来源域名、不预设字段清单。
硬规则：绝不允许虚构链接：如果某条事实没有真实命中的可点击 URL，请把它写进"不确定性"或"缺失字段"，不要给它编造 [src: ...]。
```

### 2.3 Bridge 默认改 fast + stale-busy watchdog

`scripts/deepseek-web-client.js:273` 把默认从 `expert` 改成 `fast`。

`scripts/deepseek-web-bridge.js` 增加了三层 stale 保护：
- 单个 `/search` 请求用 `Promise.race` 套 `MAX_INFLIGHT_MS` (默认 = WAIT_TIMEOUT_MS + 60s = 210s) 硬超时
- 10s 周期巡检 `setInterval`，超时即 `forceResetInFlight`
- `/health` 调用本身也触发 stale 检查
- `/health` 新增 `busyForMs / maxInFlightMs` 字段方便 debug

会话过程中我们手动遇到一次 bridge 卡在 `busy:true` 永不释放，必须 kill 重启。这套 watchdog 直接预防同类问题。

### 2.5 审核循环 fail-fast（复读检测）

`MeetingWorkflowService.java` 新增 `isRejectionLoopStagnant(stageRun, currentRejectComment)`：
- 取最近 3 次 (含当前) REJECT 文本
- 用字符 bigram 做 Jaccard 相似度
- 任意一对相似度 ≥ 0.55 → 判定复读 → 直接 `concludeManualWorkflow` 收尾，附 `REJECT_STAGNANT` outcome

只在**自动审核**路径生效（line ~2143）；人工反复 reject 不拦截（人是有意为之）。

## 3. 本次会话的关键发现（必读，影响后续设计）

### 3.1 DeepSeek 网页"专家模式" vs "快速模式"实测对比

用同一只股票 (宁德时代 300750)、同一日期、同一份新 prompt：

| Bridge mode | searchEnabled UI | newLinkCount | 模型给的"当前股价" | 引用风格 |
|---|---|---|---|---|
| expert | true (按钮亮着) | **0** | 268 / 350 / 428.87 元（编） | 内部 `[来源1]` (旧 prompt) 或无 (新 prompt) |
| **fast** | false (按钮不可见) | **4** | 内嵌真实数据 (2025 营收 4237 亿，Q1 营收 1291 亿) | DeepSeek 内部编号 `-\n7`, `-\n2` 等 |

抓到的真实 URL（meeting 44）：
1. `http://stock.finance.sina.com.cn/.../rptid/829653180264/...`
2. `https://stock.stockstar.com/report/data_all_issqyrxyrqrxqwqtpvrpr.html`
3. `https://www.21jingji.com/article/20260316/herald/...`
4. `https://300750.sz/`

**结论：DeepSeek 网页版的"专家模式"=纯推理模式，不调联网搜索 agent**。这与界面 UI 显示完全相反，是 DeepSeek 平台行为，不是 bridge bug。

### 3.2 LLM 路径的真实"幻觉"边界

即便 fast 模式拿到真实 URL，模型仍然会**夹带训练数据中的"准事实"**（如"宁德时代 39.2% 全球市占率"）——这些数字在历史财报中存在但可能不是 2026 当前真值。

幻觉的层次：
1. ❌ **已治愈**: 编造 `[来源1]` 等假引用（删除定向来源约束后消失）
2. ⚠️ **未治愈但已可感知**: 把训练数据中的旧事实当成"当前事实"
3. 🔴 **fast 模式都治不了的**: 当前股价、最新季报这种实时数据，模型仍会编（即便它声称在引用 URL）

对应 3 的彻底治法（**未实施**）：把"当前价格 / 最新季报"类查询走 Serper（可控 site:），不走 Web。

## 4. 未做但有价值的优化（按优先级）

### 4.1 关键数据走 Serper（中-高价值，未做）
当前 Serper key 已配（看 §11）。建议：
- API 模型从 deliverable 中抽出"需要近实时核验的字段"（股价、最新季报数字、政策日期）
- 这些走 Serper 定向搜（如 `site:eastmoney.com 宁德时代 2026Q1`）
- 把 Serper 返回的真实 snippet 注入到二次合成提示词

### 4.2 链接 HEAD 校验（低-中价值，未做）
fast 模式下 model 偶尔会输出 `[src: url]`，但绝大部分用 DeepSeek 内部编号 `-\n7`。HEAD 校验对当前输出模式价值有限，但如果未来 prompt 进一步引导模型输出标准 URL，HEAD 校验仍然有用。

### 4.3 Submission 内容自动加"数据可信度"前置标签（中价值，未做）
基于 `newLinkCount / judge 结果 / 编造引用计数`，在 submission 文本最前面加一行：
```
[可信度：搜索命中 4 条来源 / judge 已通过 / 0 处编造引用]
```
让前端/用户看一眼就知道这次输出靠不靠谱。

### 4.4 `quickMode / bridgeMode` 持久化的 NULL 问题（低价值，未做）
代码已加但是因为运行后端实例的 class 加载时序，DB 显示 NULL。重启后端就好。如果后端长期不重启，需要额外排查 SearchMeta 字段流转。

## 7. 用户偏好（持续遵守）

- **不要 stock/topic 关键词硬编码**。任何"如果是股票就 X"的逻辑都是反模式

- **当前实时数据仍会幻觉**。fast 拿到真实 URL，但模型仍可能把 2024 年的市占率说成 2026 现状。彻底修复需要 §4.1 的 Serper 接入。
