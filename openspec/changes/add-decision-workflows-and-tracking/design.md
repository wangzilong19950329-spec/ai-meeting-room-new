## Context

当前系统以 `ai_meeting_room` 为中心，通过 `MeetingRoomService` 和 `MeetingOrchestratorService` 执行固定的多轮辩论、投票和结论收敛流程。这个模型适合“同一场里完成讨论”的场景，但对以下需求支持不足：

- 结论依赖会后补证、长期跟踪或外部数据更新；
- 会议必须按预定义阶段推进，而不是所有议员都参与同一种轮次讨论；
- 某个阶段可能需要人工审核、打回、返工和重新提交；
- 会议结束后继续追问时，需要基于旧结论版本和追踪结果重开，而不是把所有后续工作塞进自由文本。

这次设计需要在不破坏现有普通会议能力的前提下，引入一层可编排工作流和一层独立追踪项模型。目标不是把系统变成通用 BPM 平台，而是支持“决策型会议”的常见阶段化流程，并让会议和会后追踪形成闭环。

约束与前提：

- 当前后端是 Spring Boot + MyBatis + MySQL/MariaDB，适合显式建表和服务编排，不适合一次性引入重型流程引擎。
- 历史会议数据已在生产环境存在，迁移策略必须允许旧数据继续按默认流程读取。
- 现有人类介入、结论版本、项目记忆能力已经开始形成，需要与新的工作流/追踪项模型兼容，而不是推翻重做。

## Goals / Non-Goals

**Goals:**
- 给会议定义显式流程模板、阶段节点、流转条件和打回路径。
- 让一次会议可以在“进行中、等待补证、等待审核、已结论、已重开”之间稳定流转。
- 将会议产出的后续事项沉淀为独立追踪项，支持责任归属、状态推进、证据补充和重开条件。
- 让现有固定辩论模式成为一个默认工作流模板，而不是唯一执行方式。
- 为前端提供可见的流程状态和追踪状态，支持后续逐步补充流程设计器和阶段执行界面。

**Non-Goals:**
- 不把系统扩展成通用企业 BPM/审批平台。
- 不在第一阶段支持任意脚本化条件表达式或图形化拖拽式流程设计器。
- 不在第一阶段解决所有权限和组织协作模型问题，只定义与会议流程直接相关的角色/执行者语义。
- 不要求一次性把历史会议全部补齐为结构化工作流实例。

## Decisions

### 1. 用“默认模板 + 可选自定义模板”替换固定会议主流程

决定：
- 新增 `workflow_template`、`workflow_stage_template`、`workflow_transition` 抽象。
- 每次会议创建时绑定一个流程模板；如果用户未选择，则自动绑定系统默认模板。
- 当前“多轮辩论 -> 投票 -> 共识 -> 结论”被实现为系统默认模板，以保持兼容。

原因：
- 这样可以保留现有会议能力，同时给阶段化流程提供统一入口。
- 相比直接把现有 `MeetingRoomService` 拆成大量条件分支，模板化更适合后续增加分析、复核、终审、返工等结构。

备选方案：
- 直接在 `ai_meeting_room.status` 和服务层里硬编码更多状态。
  - 未选用，因为很快会把流程逻辑散落到多个 `if/else`，难以复用和扩展。

### 2. 区分“模板定义”和“运行实例”

决定：
- 模板层描述静态结构：阶段类型、执行角色、进入条件、通过条件、回退路径。
- 实例层描述运行时状态：当前阶段、阶段产物、执行记录、退回原因、重开来源。
- 引入 `meeting_workflow_run` 和 `meeting_workflow_stage_run` 作为会议执行态。

原因：
- 会议运行数据必须可追溯，不能直接写回模板。
- 同一个模板会被多次复用，每次会议需要独立记录阶段执行和返工轨迹。

备选方案：
- 只在会议表里记录当前阶段和少量 JSON。
  - 未选用，因为后续阶段审计、打回链路和统计都需要结构化实例表。

### 3. 追踪项作为独立实体，而不是会议总结中的文本片段

决定：
- 新增 `meeting_tracking_item`，并允许它关联来源会议、来源阶段、责任人、到期时间、证据更新和重开条件。
- 追踪项支持独立状态流转，例如 `OPEN / IN_PROGRESS / BLOCKED / READY_FOR_REVIEW / VERIFIED / REJECTED / CLOSED`。
- 阶段可以声明“完成后必须创建追踪项”或“仅当关联追踪项满足条件才可进入下一阶段/重开会议”。

原因：
- 如果追踪项只是结论文本的一部分，系统无法知道哪些事项已完成，更无法自动推动会议继续。
- 独立实体之后，会议才能和会后验证形成真正闭环。

备选方案：
- 先只在 `decision_artifact` 里加数组字段保存待办。
  - 未选用，因为这只能展示，无法支持责任、证据、状态和触发逻辑。

### 4. 阶段产物统一建模为“提交物”，而不是强依赖原有 opinion/vote

决定：
- 引入统一阶段提交模型，例如 `meeting_stage_submission`，保存某阶段的分析稿、复核意见、审核结论、打回说明等。
- 现有 `ai_meeting_opinion` 和 `ai_meeting_vote` 仍保留，用于默认辩论模板的详细过程记录。
- 新流程阶段优先依赖阶段提交物，而不是强行把所有阶段都映射成 opinion/vote。

原因：
- “分析”、“核对”、“终审”、“补证完成”这些动作的语义与普通辩论发言不同。
- 保留 opinion/vote 是为了兼容已有会议回放和结论机制，但新流程不能被旧表结构绑死。

备选方案：
- 复用 `ai_meeting_opinion`，通过新增 `opinion_type` 承载所有阶段语义。
  - 未选用，因为它会让原本面向辩论的表过度膨胀，且阶段级别的通过/打回/返工语义难以表达。

### 5. 会议状态与工作流状态分层管理

决定：
- `ai_meeting_room.status` 保持高层会议态，如 `CREATED / IN_PROGRESS / CONCLUDED / REOPENED / CANCELLED`。
- 工作流运行表维护细粒度阶段态，如 `PENDING / ACTIVE / WAITING_REVIEW / REJECTED / COMPLETED / BLOCKED_BY_TRACKING`。
- 会议详情接口聚合返回高层状态和当前阶段状态，前端同时展示。

原因：
- 会议态对列表和全局概览足够，但阶段执行需要更细粒度的状态机。
- 分层后不会迫使所有界面都理解阶段内部细节。

备选方案：
- 用单一状态枚举覆盖会议和阶段语义。
  - 未选用，因为状态数会迅速膨胀，且不同页面关心的粒度不同。

### 6. 第一阶段采用受限的流程 DSL，而不是图形化设计器

决定：
- 流程模板先使用结构化 JSON/表配置表达，包含阶段顺序、可选执行者类型、通过条件和回退目标。
- 前端第一阶段只做模板选择与运行展示，不做自由拖拽流程设计器。

原因：
- 当前最急需的是把流程语义接入系统，而不是先做复杂的设计器。
- 受限 DSL 更容易测试、版本化和审查，也更适合 OpenSpec 驱动迭代。

备选方案：
- 直接上图形化流程编排器。
  - 未选用，因为前后端改动过大，且会拖慢核心能力上线。

## Risks / Trade-offs

- [流程模型过于抽象，第一版落地慢] → 先约束支持的阶段类型和流转模式，从“默认模板 + 少量可配置模板”起步。
- [旧的辩论式会议与新的阶段式会议双轨并存，服务层复杂度上升] → 明确默认模板适配层，把旧流程包成模板执行器，避免两套完全独立逻辑。
- [追踪项与会议重开关系定义不清，容易出现重复触发] → 引入显式重开条件和去重规则，每次重开记录来源追踪项和来源结论版本。
- [前端一次性承载过多新概念，交互复杂] → 第一阶段以“查看当前阶段 + 执行动作 + 查看追踪项”为主，流程设计能力后置。
- [数据迁移影响已有线上会议] → 新表增量引入，老会议默认懒初始化工作流实例，不强制重写历史数据。

## Migration Plan

1. 先引入新表和默认模板数据，不改动历史会议数据结构。
2. 会议创建逻辑改为显式绑定模板；如果请求未指定模板，则自动绑定系统默认模板。
3. 对历史会议采用“按需补实例”策略：首次读取详情或继续会议时，为其生成默认工作流实例。
4. 阶段提交物、追踪项和重开机制先用于新会议；历史会议仅在用户继续追问或显式迁移时接入。
5. 完成新详情接口聚合后，再逐步让前端展示当前阶段、追踪项和流程轨迹。
6. 回滚策略：保留旧会议主流程入口；若新工作流执行异常，可将会议回落到默认模板的兼容路径。

## Open Questions

- 第一阶段是否允许一个阶段由多个执行者并行提交，还是只支持串行/全员完成后汇总？
- 追踪项的责任人第一阶段是只支持“用户/主持人/指定议员模板”，还是需要直接接入更细粒度的成员体系？
- 阶段通过条件采用固定枚举（如全部提交、一致性通过、审核通过）是否足够，还是需要早期支持简单条件表达式？
- 会议重开时，是否总是从指定阶段重新开始，还是有场景需要只更新结论而不重跑中间阶段？
